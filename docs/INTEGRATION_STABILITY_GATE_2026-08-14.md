لا تعتمد المنصة بعد بوصفها جاهزة للتشغيل الحرج دون تحفظ؛ ما زالت أربعة شروط تشغيلية تحتاج إجراء المالك: تفعيل نسخ احتياطي إنتاجي قابل للاستعادة، توفير جلسة آمنة لفحص قاعدة البيانات الحية، تنفيذ قبول مستخدم مسجل لكل دور على الإنتاج، وتثبيت نسخة الإنتاج في Git.

## الإصلاحات المنفذة

1. صححت خاصية دالة الملخص اليومي القرآني من `IMMUTABLE` إلى `STABLE` في Migration رقم `0026`، وطبقت على المشروع المرتبط.
2. أصبح `supabase db lint --linked --level warning` يمر بلا أخطاء في المخطط.
3. منعت تسجيل Service Worker على `localhost` لتجنب التخزين القديم أثناء التطوير، ورفعت إصدار ذاكرة الإنتاج إلى `zat-khail-v28`.
4. أضيفت أيقونة الموقع وأيقونتا PWA بمقاسي 192 و512، وربطت بجميع الصفحات والـ manifest والإشعارات.
5. صححت أنماط حقول اسم المستخدم لتتوافق مع Unicode Sets في المتصفحات الحديثة.
6. أصلحت لوحة ولي الأمر في المعاينة المحلية كي لا تنفذ طلبات مجهولة مرفوضة إلى Supabase.
7. أضيفت اختبارات رجوع لهذه المشكلات حتى لا تعود مستقبلا.

## المسارات الوظيفية المختبرة

- المدير: إنشاء حساب طالب تجريبي وحذفه مع تأكيد اسم المستخدم.
- المعلم: فتح إدارة تقارير القرآن، مراجعة التقارير، المحاسبة، طلبات التمديد، وسجل الطالب.
- الطالب: منع إنجاز تقرير اليوم عند وجود تقرير سابق متأخر، طلب تمديد، إكمال التقرير المتأخر، وتحديث رسالة إنجاز اليوم.
- Excel: رفع الملف الحقيقي `موقع مركز ذات خيل.xlsx`، وتحليل 37 تقريرا بلا أخطاء، ثم فحص التعارض والاعتماد في المعاينة.
- ولي الأمر: عرض الابن التجريبي وربطه محليا من دون أخطاء شبكة.
- العرض: تسجيل الدخول، لوحات المدير والمعلم والطالب وولي الأمر، الإعدادات، ومساحة الحلقة على الهاتف وسطح المكتب.

## فحوص الأمان والتخزين

- صحة Supabase Auth متاحة وتعيد استجابة صحيحة.
- بيانات دخول غير صحيحة تعيد `401` ورسالة عامة لا تكشف وجود الحساب.
- دالة المدير الطرفية ترفض الطلب بلا جلسة مصرح بها برمز `401`.
- RPC القرآني المحمي يرفض دور `anon`.
- قائمة حاويات Storage لا تكشف أسماء حاويات خاصة للمستخدم المجهول.
- النطاق الإنتاجي يرسل: `X-Content-Type-Options: nosniff` و`X-Frame-Options: DENY` و`Referrer-Policy: strict-origin-when-cross-origin` وقيود الكاميرا والميكروفون والموقع، مع HSTS لمدة سنتين.

## المتطلبات المفتوحة قبل الاعتماد التشغيلي

### 1. النسخ الاحتياطي

أظهر Supabase أن WAL-G مفعّل، لكن `PITR` غير مفعّل وقائمة النسخ الفيزيائية المتاحة فارغة وقت الفحص. يلزم أحد الخيارين:

- تفعيل خطة Supabase تدعم النسخ اليومية أو PITR، وهو الخيار الأنسب للإنتاج.
- أو إنشاء نسخ منطقية دورية مشفرة خارج Git، مع تجربة استعادة فعلية موثقة.

لا تكفي نسخة 2026-08-09 وحدها لأنها لا تشمل أحدث بيانات ومهاجرات الإنتاج.

### 2. فحص قاعدة البيانات الحية

تعذر تشغيل `supabase inspect db` والنسخ المنطقي واختبارات SQL المحلية لعدم توفر `SUPABASE_DB_PASSWORD` وعدم وجود Docker Desktop محلي. المطلوب إدخال كلمة مرور قاعدة البيانات في جلسة PowerShell آمنة، أو تشغيل Docker Desktop، ثم تنفيذ:

- فحص الجداول الكبيرة والأقفال والاستعلامات الشاذة.
- التحقق من سجل Cron الفعلي وجدول مهمة الملخص اليومي.
- تشغيل ملفات `tests/sql` على بيئة محلية معزولة.
- إنشاء نسخة جديدة واختبار استعادتها.

لا ترسل كلمة مرور قاعدة البيانات داخل المحادثة.

### 3. قبول الإنتاج بحسابات حقيقية

تم اختبار واجهات الأدوار كاملة في المعاينة، واختبرت حدود API في الإنتاج، لكن لم تنفذ دورة كتابة كاملة على الإنتاج بحسابات اختبار مسجلة حتى لا تتغير بيانات حقيقية دون إذن. يلزم تجهيز حساب اختبار مؤقت لكل من المدير والمعلم والطالب، ثم تنفيذ دورة: إنشاء حساب، إلحاق بحلقة، استيراد خطة، اعتماد تقرير، تسليم طالب، مراجعة معلم، ثم حذف أو إخفاء بيانات الاختبار.

### 4. تثبيت نسخة الإنتاج في Git

النشر الحالي صحيح ومتاح، لكن Vercel يسجله من شجرة عمل تحتوي تعديلات محلية (`gitDirty: 1`). يجب بعد مراجعة الفروقات إنشاء Commit واضح ودفعه إلى المستودع؛ حتى تصبح نسخة الإنتاج قابلة لإعادة البناء والتدقيق من Git. لا يدفع أي تغيير إلى GitHub قبل موافقة المالك الصريحة.
